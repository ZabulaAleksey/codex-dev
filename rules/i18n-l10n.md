# Глобальная Internationalization / Localization Policy

Эта policy является межпроектным стандартом ДЕВ для всех продуктов с пользовательской
поверхностью. Она задаёт архитектурные инварианты `i18n` / `l10n`, а конкретный project
repository хранит только поддерживаемые языки и локали, выбранный stack, исключения и
проверяемые требования реализации.

## Область применения

Policy применяется к UI, публичному CLI, пользовательским уведомлениям, отчётам, письмам и
другим поверхностям, где продукт показывает человеку текст или locale-dependent данные.
Библиотека либо infrastructure repository без пользовательской поверхности может зафиксировать
`N/A` с причиной в архитектуре или project context; при появлении такой поверхности применимость
пересматривается.

Полный контракт принадлежит только этому файлу. Project `AGENTS.md`, `DESIGN.md`, `SPEC`,
`ARCHITECTURE.md` и `DECISIONS.md` ссылаются на него и описывают только project-specific delta,
не копируя глобальное правило.

## Термины

- Internationalization (`i18n`) — архитектурная готовность продукта добавлять языки и локали
  без переписывания business logic и пользовательских компонентов.
- Localization (`l10n`) — конкретная адаптация ресурсов и поведения под выбранные язык и регион.
- `language` описывает язык, а `locale` — язык вместе с региональными правилами. Например,
  `en-US` и `en-GB` используют один language, но различаются форматами и региональными нормами.

Язык проектной документации из `AGENTS.md` не определяет язык продукта и не заменяет его
`language` / `locale` contract.

## Архитектурные инварианты

### Пользовательские строки

- Пользовательские строки не должны быть жёстко прибиты к business logic. Компоненты и
  presentation layer используют ключи и translation resources: `t("...")`, locale-файлы или
  эквивалент выбранного стека.
- Если итоговый текст формирует client, backend передаёт стабильный message code и параметры,
  а не требует распознавать локализованную строку. Если локализация принадлежит server-side
  поверхности, эта граница фиксируется в архитектуре и тестируется там.
- Brand names, protocol literals и иной намеренно непереводимый текст допустимы как явные
  исключения. Материальное исключение документируется; оно не должно маскировать случайный
  hardcode.
- User-generated content не считается translation resource и не переводится автоматически без
  отдельного продуктового требования.

### Locale-dependent данные

Доменные значения хранятся и передаются в канонической форме, а locale-specific представление
формируется на presentation boundary. `l10n` не сводится к переводу текста и по применимости
охватывает:

- даты и время, calendar conventions и часовые пояса;
- числа, десятичные и группирующие разделители;
- валюты и денежные форматы;
- единицы измерения;
- plural rules и grammatical variants;
- сортировку и collation;
- адреса и телефонные номера;
- другие locale-dependent данные продукта.

Locale не должен неявно подменять отдельные доменные значения. В частности, валюта, единица,
страна и часовой пояс хранятся или выбираются явно, если бизнес-правила не доказали безопасную
однозначную связь с locale.

### Выбор locale и fallback

- Проект задаёт детерминированный locale resolution order и один обязательный fallback locale.
  Явный выбор пользователя имеет приоритет над сохранённой настройкой и device/request hint,
  если project SPEC не фиксирует обоснованное иное поведение.
- Отсутствующий либо неполный перевод обрабатывается предсказуемо: lookup переходит по
  документированной fallback chain, а диагностический сигнал сохраняет missing key и locale.
  Production UI не должен молча показывать пустую строку, stack trace или иной небезопасный
  технический текст.
- Retry, degraded mode и fail-open/fail-closed semantics остаются во владении
  `rules/fallback-policy.md`; этот документ задаёт только locale-specific fallback delta.

### Layout, RTL и доступность

- Layout не предполагает фиксированную длину перевода. Компоненты учитывают text expansion,
  переносы, truncation policy и изменение размеров элементов.
- Для заявленных RTL-языков используются direction-aware layout и logical properties; порядок,
  выравнивание и иконки проверяются отдельно. Направление отдельного фрагмента данных не должно
  ошибочно наследоваться только из направления всей страницы.
- Locale switch, fallback и direction changes не должны ухудшать keyboard navigation,
  screen-reader labels и другие применимые accessibility guarantees.

## Project-specific delta

Для пользовательского продукта КАРКАС фиксирует только конкретику:

- `SPEC` — поддерживаемые `language` / `locale`, resolution/fallback contract,
  locale-dependent product rules и acceptance criteria;
- `DESIGN.md` — locale switch UX, text expansion, RTL и состояния missing/partial translation;
- `ARCHITECTURE.md` — выбранную библиотеку, границы resource loading, caching, server/client
  responsibility и хранение предпочтений, если это архитектурно существенно;
- `DECISIONS.md` — значимые исключения, миграцию legacy hardcode и решения со trade-offs;
- `TESTING.md` — project-specific test matrix и реальный пользовательский сценарий.

Project `AGENTS.md` может только маршрутизировать к этому канону и локальным delta. Он не должен
перечислять полный глобальный набор правил повторно.

## Greenfield, brownfield и завершённые stages

Greenfield-продукт вводит i18n boundary с первого пользовательского vertical slice. Допустимо
начать с одной полностью рабочей production locale, если slice уже содержит реальные resources,
locale resolution, fallback и locale-aware formatting, а pseudo-locale либо alternate test locale
доказывает добавление следующей locale без изменения business logic и компонентов. Пустой
interface, mock lookup или будущая translation infrastructure такого evidence не дают.

В brownfield repository сначала выполняется read-only gap audit. Массовая замена строк не
производится автоматически: новые и изменяемые поверхности соблюдают policy, а подтверждённый
legacy debt получает явный scope, приоритет и migration evidence. Фактический код и принятые
тесты остаются source of truth текущего поведения.

Stage может считать свой i18n/l10n slice завершённым только когда его default-locale path,
fallback и заявленные locale-dependent правила исполнимы и проверены без будущего компонента.
Добавление новых переводов в будущем расширяет работающую l10n, но не должно впервые включать
обязательную i18n infrastructure предыдущего stage. Иначе применяются статусы `scaffolded`,
`implemented_unverified`, `partial` или `blocked`, а не `completed` / `verified` / `DONE`.
Полные lifecycle/evidence semantics этих статусов остаются во владении `rules/governance.md`.

## PASS evidence

Масштаб evidence соответствует затронутой поверхности, но применимый контракт включает:

- static/review check новых и изменённых пользовательских строк;
- unit tests locale resolution, formatting, plural rules и fallback;
- component tests missing translation, text expansion и RTL, когда такие поверхности заявлены;
- integration tests границы resource loading и server/client responsibility;
- живой E2E locale switch и locale-dependent output для поддерживаемой multi-locale поверхности.

Если живой product path ещё отсутствует, structural test подтверждает только архитектурную
подготовку. Он не закрывает пользовательский E2E и не повышает stage до `DONE`.
